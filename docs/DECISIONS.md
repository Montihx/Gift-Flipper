## D-001 Отдельный проект, Mini App — основной интерфейс (2026-11-08)
Статус: принято
Контекст: нужен свой флиппер NFT-подарков Telegram.
Решение: самостоятельный проект. Все настройки и просмотр — в Mini App. Бот — только пуши и действия в один тап (Купить, Пропустить, Открыть, Пауза, Panic, итог дня).
Альтернативы: управление целиком кнопками бота (как у открытых аналогов) — отклонено, неудобно для гибких фильтров.
Последствия: нужен API + фронтенд с первого MVP.

## D-002 Чужой код не запускаем, переписываем идеи (2026-11-08)
Статус: принято
Контекст: часть найденных «снайперов» распространяется с .exe и накрученными звёздами — типичная схема кражи сессий.
Решение: из чужих репо берём только описания API и алгоритмы, код пишем сами. Подозрительные репо читаем только как текст.
Последствия: дольше на этапе 2, но нет риска утечки сессии и кошелька.

## D-004 Способ чтения чужих репозиториев для завершения Этапа 0 (2026-11-09)
Статус: принято (2026-11-09, владелец проекта). Уточнение по факту: агент работает в облачном контейнере Claude Code, а не локально; `api.github.com` и веб-страницы `github.com` там по-прежнему закрыты, но `git clone` по HTTPS и `raw.githubusercontent.com` доступны. Поэтому применён вариант (b): `git clone --depth 50` в отдельные пустые каталоги вне проекта (scratchpad сессии), чтение только как текст, без запуска и без установки зависимостей. Репозитории разделов I и J не клонировались — только README через raw.
Контекст: в сессии закрыты `gh api` и `raw.githubusercontent.com`; через WebFetch читаются только главные страницы части репозиториев. Исходный код (эндпоинты покупки/продажи/баланса, флор topcvetok) не прочитан.
Решение: выбрать одно: (a) открыть `github.com`, `raw.githubusercontent.com`, `api.github.com` в allowlist; (b) разрешить `git clone --depth 1` в отдельные пустые каталоги, читать только как текст, не запускать, не ставить зависимости, не клонировать репозитории разделов I и J (их — только README).
Альтернативы: считать недостающее самим по трафику Mini App маркетов (долго, нужен владелец и его сессия); пропустить недостающее.
Последствия: без (a) или (b) клиенты покупки/листинга писать нельзя — формат запросов не известен. AGENTS.md §4.3 («не запускать чужой код») остаётся в силе в обоих вариантах.
Источник идеи: сам процесс Этапа 0.

## D-005 Единый провайдер токенов на Telethon (2026-11-09)
Статус: принято (2026-11-09, владелец проекта)
Контекст: все три маркета авторизуются через `initData` Mini App (Portals: `Authorization: tma <initData>`; MRKT: `POST /api/v1/auth {"data": initData}` → token; Tonnel: `web-initData`). Сроки жизни токенов не подтверждены.
Решение: модуль `markets/auth.py` получает `initData` через Telethon-сессию владельца (аналог `messages.requestAppWebView`; для Portals — бот `portals`, short_name `market`), кэширует токен в секретном хранилище и перевыпускает при ответе 401 или по запасному таймеру, а не по предположению о сроке.
Альтернативы: копирование токена из DevTools вручную (отклонено: ручной шаг и утечки); зависимость от `update_auth()` из portalsmp (отклонено, см. D-007).
Последствия: нужен один постоянный Telethon-клиент и защита файла сессии (права 600, AGENTS.md §4.2). Конкретные вызовы Telethon проверить на Этапе 2.
Источник идеи: bleach-hub/portalsmp, boostNT/Portals-API, boostNT/MRKT-API, bleach-hub/tonnelmp.

## D-006 HTTP-клиент маркетов: curl_cffi с имитацией браузера (2026-11-09)
Статус: принято (2026-11-09, владелец проекта)
Контекст: для Tonnel README рекомендует `curl_cffi` с `impersonate="chrome"`; amrkt по умолчанию имитирует TLS Chrome и ротирует User-Agent. AGENTS.md §2 допускает `aiohttp`/`curl_cffi`.
Решение: клиенты всех трёх маркетов — `curl_cffi` (async) с настраиваемым профилем `impersonate`, заголовками и опциональным прокси; `aiohttp` оставляем для прочих HTTP-задач.
Альтернативы: `aiohttp` для Portals/MRKT и `curl_cffi` только для Tonnel (возможно, после проверки, нужна ли имитация остальным).
Последствия: зависимость от профилей `impersonate`; тесты — только на MockClient и фикстурах.
Источник идеи: boostNT/Tonnel-API, TheBrainAir/amrkt.

## D-008 Временный бюджет запросов к маркетам (2026-11-09)
Статус: принято (2026-11-09, владелец проекта)
Контекст: реальные лимиты маркетов не известны.
Решение: до замеров — не чаще 1 запроса списка листингов на маркет раз в 5 с, ≤ 1 запрос/с суммарно на маркет, backoff с jitter на 429/5xx, таймаут 10 с. Параметры в настройках.
Альтернативы: агрессивный опрос (отклонено: риск блокировки).
Последствия: возможна задержка обнаружения сделок; пересмотр на Этапе 9.4. Это решение проекта, а не данные маркетов (`MARKETS.md` §6).
Источник идеи: AGENTS.md §4.5.

## D-009 Комиссии — конфигурация с флагом «проверено» (2026-11-09)
Статус: принято (2026-11-09, владелец проекта, при условии безопасности: правило только запрещает покупки до проверки комиссий)
Контекст: источники расходятся (Portals 0/2.5/5%; Tonnel +10% покупка и 3–4% продажа; MRKT 2/5%), ничего не проверено (`MARKETS.md` §5).
Решение: `pricing/fees.py` читает комиссии из конфига, каждая запись имеет поле `verified: bool` и источник. Пока `verified=False`, чистая прибыль в Mini App и пушах помечается «оценка, комиссии не проверены», режимы confirm/auto для такой пары маркетов не включаются.
Альтернативы: зашить цифры из заданий (отклонено: не подтверждены).
Последствия: проверка комиссий владельцем на минимальных суммах — условие входа в Этап 7.
Источник идеи: раздел I задания, bleach-hub/tonnelmp.

## D-010 Оценка Telegram — вспомогательный сигнал (2026-11-09)

Последствия: нужен slug каждого подарка и живая пользовательская сессия. Проверено 2026-11-09: Telethon 1.45 (слой 229) содержит `payments.GetUniqueStarGiftValueInfoRequest`.

## D-012 Цены: nanoTON int, парсинг строк через Decimal (2026-11-09)
Статус: принято (2026-11-09, владелец проекта)
Контекст: MRKT использует nanoTON (amrkt), Portals отдаёт цены строкой (`"44"`, `"31.43"`), Tonnel — цена в TON без комиссии (единицы не подтверждены).
Решение: каждый клиент нормализует цену в nanoTON (int) через `Decimal`, без float; единицы каждого маркета фиксируются в фикстурах и проверочных тестах после записи живых ответов.
Альтернативы: хранить как пришло (отклонено: ошибки округления).
Последствия: единицы Portals/Tonnel подтверждаются записью фикстур на Этапе 2.
Источник идеи: AGENTS.md §5, TheBrainAir/amrkt, bleach-hub/portalsmp.

## D-014 Tonnel: события через WebSocket `gifts.coffin.meme` (2026-11-09)
Статус: принято (2026-11-09; владелец поручил выбор агенту). Пересматривает часть D-011 «Tonnel без WebSocket на старте».
Почему так: WS даёт и новые листинги, и продажи (`sale.completed`) без затрат бюджета запросов; без него медиана продаж Tonnel за 24 ч недоступна. Опрос `pageGifts` остаётся как резерв, поэтому отказ WS не ломает watch-режим.
Контекст: при принятии D-011 WebSocket Tonnel не был подтверждён. Во втором проходе Этапа 0 он найден в коде topcvetok (2026-11): `wss://gifts.coffin.meme/api/marketplace/ws`, события `listing.created`, `listing.price_changed`, `sale.completed`, догонка `GET /api/marketplace/events?after=&limit=100`. Тот же домен tonnelmp использует для покупок — по косвенным признакам бэкенд Tonnel. Подписка не требует авторизации (из кода topcvetok).
Решение: на Этапе 2 Tonnel = опрос `pageGifts` (D-008) **плюс** WebSocket событий как основной источник новых листингов и продаж; при обрыве — догонка по `events?after=` и опрос. Подключение одно, в бюджет запросов не входит. Включать только после проверки на живом соединении (только чтение).
Альтернативы: только опрос (медленнее, нет продаж для медианы 24 ч); партнёрские агрегаторы (Swift Gifts — платный ключ).
Последствия: продажи Tonnel для `pricing/sales.py` берутся из `sale.completed`. Риск: сторонний домен может смениться.
Источник идеи: topcvetok/telegram-gift-watch (`tonnel_watch.py`), bleach-hub/tonnelmp.

## D-016 Одна ветка на весь проект; живые фикстуры — на ПК владельца (2026-11-09)
Статус: принято (2026-11-09, владелец проекта)
Контекст: AGENTS.md §5 требует «одна задача = одна ветка = один PR». Владелец: всё в одной ветке, иначе проект не собрать. Агент в облачном контейнере не должен получать Telethon-сессию.
Решение: (1) Этапы 1–6 ведутся в одной ветке `claude/upbeat-hamilton-2rqux1`, этап = серия маленьких коммитов с префиксом `stageN:`/областью; PR — один на ветку (обновляется по мере работы). (2) Запись живых фикстур (Этап 2, только запросы на чтение по списку, согласованному владельцем) выполняет новый агент на ПК владельца, где лежит сессия. До этого клиенты пишутся и тестируются на фикстурах, собранных из кода/фикстур источников и помеченных `"_source": "code:<repo>"`; парсеры терпимы к лишним полям. Передача контекста — `docs/HANDOFF.md`.
Альтернативы: сессия в облачном `data/` (отклонено: риск утечки).
Последствия: AGENTS.md §5 уточнён; пометка «проверено на живом ответе» появится только после шага на ПК.

## D-017 Запрет записи на уровне HTTP: белый список путей чтения (2026-11-09)
Статус: принято (агент, в рамках AGENTS.md §4.1 — уточнение реализации, не новое правило)
Контекст: AGENTS.md §4.1 — эндпоинты покупки только через `execution.spend()`. Клиенты маркетов на Этапе 2 не должны иметь технической возможности вызвать покупку/листинг/вывод, даже по ошибке.
Решение: `MarketHttp` проверяет каждую пару (метод, путь) по `ReadOnlyGuard` — явному белому списку `READ_ROUTES` каждого маркета; всё остальное отклоняется до отправки (`ReadOnlyViolation`). Тест проверяет, что в списках нет путей покупки/листинга/вывода. На Этапе 7 пути записи появятся только в `execution/` с отдельным guard.
Альтернативы: чёрный список путей покупки (отклонено: новый путь записи прошёл бы молча).
Последствия: каждый новый путь чтения добавляется явно, с тестом.

## D-019 Параметры оценки по умолчанию (2026-11-09)
Статус: принято (агент; параметры настраиваются, пересмотр после живых данных в режиме watch)
Контекст: AGENTS.md §8 задаёт кластерный флор; остальные пороги источники задают по-разному (topcvetok: N=5/3, разброс 8%/20%; раздел I: кластер ≥3 в +10%, скачок 25%/ч, «слишком дёшево» < 25%).
Решение: `FloorConfig` — кластер 3 цены в +10%; мин. сопоставимых 3 (модель+фон, модель) и 5 (коллекция); high — кластер и ≥8 сопоставимых; без кластера — медиана 3 дешёвых (low); скачок > 25% — доверие на ступень ниже; < 25% флора — «слишком дёшево». Перепродажа = флор − 0.01 TON, ограничена медианой продаж 24 ч при ≥3 продажах. Комиссии по умолчанию — наибольшие из заявленных (Portals 0/5%/0.1 TON, Tonnel +10%/4%/0.001 TON, MRKT 0/8%/—), все `verified=false`. Перепродажа считается на всех маркетах, выбирается максимальный net.
Альтернативы: флор = минимум остальных с проверкой разброса (topcvetok) — менее устойчив к одиночным приманкам.
Последствия: оценки консервативны; прибыль помечена «оценка» до проверенной таблицы комиссий.

## D-020 Mini App: официальный telegram-web-app.js вместо @telegram-apps/sdk (2026-11-09)
Статус: принято (агент; AGENTS.md §2 помечает стек как черновик)
Контекст: нужны initData, тема, haptic, BackButton, ссылки. Всё это есть в официальном скрипте `https://telegram.org/js/telegram-web-app.js`, который сам выставляет CSS-переменные `--tg-theme-*`.
Решение: тонкая обёртка `webapp/src/telegram.js` над `window.Telegram.WebApp`; без `@telegram-apps/sdk` и без роутер-библиотек (hash-роутинг). Живые обновления — SSE поверх `fetch` (EventSource не передаёт заголовки, а initData в URL класть нельзя). Кнопка сохранения — обычная кнопка формы, а не MainButton (валидация формы и доступность).
Альтернативы: `@telegram-apps/sdk` (лишняя зависимость для MVP).
Последствия: при необходимости SDK можно подключить позже без смены API бэкенда.

## D-021 Снимок сделки в уведомлении (2026-11-09)
Статус: принято (агент)
Решение: в `alerts.payload` (JSON, миграция 0004) сохраняется снимок `Deal` на момент пуша; деньги — строки nanoTON и строки TON для показа. Карточка Mini App показывает именно то, что видел пуш. Наблюдаемые продажи пишутся в `sales` (для графика и истории).
Последствия: карточка не пересчитывается при изменении рынка; актуальность видна по статусу (ПРОДАНО/снято).
